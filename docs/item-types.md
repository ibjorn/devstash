# Item Types

Reference for DevStash's seven **system** item types — what each one is for, how it is
stored, and how it renders today.

> Generated by `/research item-types-research` on 2026-08-26.
> Sources: `context/project-overview.md`, `prisma/schema.prisma`, `prisma/seed.ts`,
> `src/lib/type-icons.ts`, `src/lib/type-colors.ts`, `src/lib/db/items.ts`,
> `src/components/dashboard/*`, plus the live Neon **development** branch
> (`br-twilight-haze-ahkkq919` / endpoint `ep-withered-thunder-ahswdzxt`).

## What a "type" actually is

There is no `type` enum. A type is a **row in the `ItemType` table** — `name`, `icon`
(a Lucide icon name), `color` (a hex string), `isSystem`, and a nullable `userId`.
System types have `userId = null` and `isSystem = true`; custom types (an unbuilt Pro
feature) would carry a `userId`.

That means icon and colour are **data, not code**. `src/lib/type-icons.ts` only maps the
seven stored icon *names* to Lucide components, falling back to `File` for anything
unknown; `src/lib/type-colors.ts` only tints a stored colour via `color-mix`. Changing a
type's look is a seed/DB change, not a code change.

A separate field, `Item.contentType` (`ItemContentType` enum: `TEXT | FILE | URL`),
decides which content columns an item uses. **`contentType` is set per item, not derived
from the type** — nothing in the schema or the seed enforces "every Snippet is TEXT",
it is a convention the seed follows.

## The seven system types

Defined in `prisma/seed.ts` (`SYSTEM_TYPES`) and verified row-by-row against the
development branch — all seven exist, all `isSystem = true`, `userId = null`, and no
custom types exist.

| Type | Icon (Lucide) | Colour | Hex | Content type | Pro | Purpose |
|---|---|---|---|---|---|---|
| **Snippet** | `Code` | Blue | `#3b82f6` | `TEXT` | — | Reusable code fragments — hooks, utilities, config blocks. The type that most wants syntax highlighting. |
| **Prompt** | `Sparkles` | Purple | `#8b5cf6` | `TEXT` | — | LLM prompts and system messages, often with `{{PLACEHOLDER}}` slots. |
| **Command** | `Terminal` | Orange | `#f97316` | `TEXT` | — | Shell one-liners and short scripts you keep re-looking-up. |
| **Note** | `StickyNote` | Yellow | `#fde047` | `TEXT` | — | Free-form Markdown notes and explanations. |
| **Link** | `Link` | Emerald | `#10b981` | `URL` | — | Bookmarked docs and references. |
| **File** | `File` | Gray | `#6b7280` | `FILE` | 🔒 | Uploaded documents (context files, templates) stored in Cloudflare R2. |
| **Image** | `Image` | Pink | `#ec4899` | `FILE` | 🔒 | Uploaded images, same storage path as File. |

Pro-only status is **not** stored on the row. It is a hardcoded set in
`src/lib/db/items.ts`:

```ts
const PRO_TYPE_NAMES = new Set(["File", "Image"]);
```

…surfaced as `ItemTypeNavItem.isPro`, which draws the `PRO` badge in the sidebar. Nothing
gates creation on it yet — during development all types are open.

## Key fields per type

Every item is one `Item` row. Which columns carry the payload depends on `contentType`:

| Field | Snippet | Prompt | Command | Note | Link | File | Image |
|---|---|---|---|---|---|---|---|
| `contentType` | `TEXT` | `TEXT` | `TEXT` | `TEXT` | `URL` | `FILE` | `FILE` |
| `content` | ✅ the code | ✅ prompt body | ✅ the command | ✅ Markdown | — | — | — |
| `url` | — | — | — | — | ✅ target URL | — | — |
| `fileUrl` | — | — | — | — | — | ✅ R2 URL | ✅ R2 URL |
| `fileName` | — | — | — | — | — | ✅ | ✅ |
| `fileSize` | — | — | — | — | — | ✅ bytes | ✅ bytes |
| `language` | ✅ highlighting | ○ rare | ✅ usually `bash` | ○ `markdown` | — | — | — |

✅ = used · ○ = optional/occasional · — = stays null

All seven columns are **nullable**. There is no DB constraint tying `contentType` to the
columns it implies — an item could carry both `content` and `url` and Postgres would not
object. Validation for that is owed to the (unbuilt) Item CRUD layer.

Live data confirms the convention holds so far: Snippets/Prompts/Commands are all `TEXT`,
Links are all `URL`, and `language` appears only on Snippets (`typescript`, `dockerfile`)
and Commands (`bash`).

## Shared properties

Every item, regardless of type, carries:

- **`id`** — cuid
- **`title`** — required, the only always-present display string
- **`description`** — optional one-liner shown under the title
- **`isFavorite` / `isPinned`** — booleans, default `false`; pinned items get their own
  dashboard section, favourites feed the stats cards
- **`userId`** — owner; indexed, and every dashboard query filters on it
- **`itemTypeId`** — the type row; indexed. **`ON DELETE RESTRICT`** (no cascade), which
  is why account deletion has to remove items before custom types
- **`collections`** — many-to-many via `ItemCollection`; an item can live in several
- **`tags`** — many-to-many via the `ItemTags` relation. `Tag.name` is globally unique
  with **no `userId`** — tags are shared across all users, a scoping decision still owed
  before Item CRUD ships
- **`createdAt` / `updatedAt`**

## Classification: text vs file vs URL

The `ItemContentType` enum splits the seven types into three storage shapes:

**TEXT — Snippet, Prompt, Command, Note (4 of 7)**
Payload lives in `content` as a plain string. No external storage, no size accounting.
These are the types that get the Markdown editor, syntax highlighting (via `language`),
and copy-to-clipboard. They are the free tier's whole surface.

**URL — Link (1 of 7)**
Payload is the `url` column; there is no body at all. Cheapest type to store, and the
only one whose "content" is a pointer somewhere else. `title`/`description` do the
describing.

**FILE — File, Image (2 of 7)**
Payload lives in Cloudflare R2; the row keeps `fileUrl`, `fileName`, `fileSize`. These
are the two Pro-gated types, and the gating tracks the storage cost rather than anything
about the content. File and Image are *identical* at the schema level — they differ only
in icon, colour, and the viewer you would build for them (preview thumbnail vs download
link).

The practical split: **TEXT types own their content, URL and FILE types reference it.**
Search, export and AI features will need to branch on exactly this, since only TEXT types
have anything locally to read.

## Display differences

Today all type-driven display is **colour and icon**, both read straight off the row.
There is no per-type layout, viewer or editor yet.

- **`ItemRow`** (`src/components/dashboard/ItemRow.tsx`) — the card border is
  `typeColorTint(color, 25)` and the icon chip is `typeColorTint(color, 10)` with the raw
  colour as foreground. The icon comes from `typeIcons[icon] ?? File`.
- **`CollectionCard`** — takes its background (`5%`) and border (`25%`) from the
  collection's **most-used** type, then renders one small icon per type present, ordered
  by usage. Empty collections fall back to `defaultTypeId`.
- **Sidebar** — one nav entry per system type with a per-user count, name pluralised by
  appending `"s"` (all seven pluralise regularly), linking to `/items/{slug}`. `File` and
  `Image` additionally get the `PRO` badge.
- **Profile** — reuses `getItemTypeNavItems` for its type breakdown.

Tints go through `color-mix(in srgb, …)` rather than hex-alpha suffixes specifically so
user-supplied custom-type colours in any CSS format keep working.

**What does *not* vary by type yet:** `ItemRow` shows title, description, tags and date
for every type identically. It never reads `content`, `url`, `fileUrl`, `fileName`,
`fileSize` or `language` — grep confirms those fields are referenced nowhere in live
`src/` code, only in the dead `src/lib/mock-data.ts`. The type-specific rendering the
project overview describes (syntax highlighting, Markdown editor, image previews,
click-through links) all still belongs to the unbuilt drawer.

## Discrepancies worth knowing

1. **Two different orderings exist.** `context/project-overview.md` lists the types as
   Snippet, Prompt, Command, Note, **Link**, File, Image. `SYSTEM_TYPE_ORDER` in
   `src/lib/db/items.ts` — which drives the actual sidebar — puts Link **last**:
   Snippet, Prompt, Command, Note, File, Image, Link. The table has no sort column, so
   that array is the only source of order.

2. **The sidebar's type links 404.** Every type links to `/items/{slug}`, but no
   `src/app/items/` route exists. Item CRUD owns it.

3. **`src/lib/constants.tsx` (named in the research prompt) does not exist.** Type
   constants are split between `prisma/seed.ts` (the canonical `SYSTEM_TYPES`),
   `src/lib/type-icons.ts` (the icon-name map), and `src/lib/db/items.ts`
   (`SYSTEM_TYPE_ORDER`, `PRO_TYPE_NAMES`).

4. **Custom types are excluded from the profile breakdown**, since `getItemTypeNavItems`
   filters `isSystem: true` — harmless while custom types are unbuilt, already logged
   against the Profile Page feature.

5. **Half the types have no data.** On the development branch: Snippet 4, Command 5,
   Link 6, Prompt 3 — and **Note, File, Image all sit at 0**. The seed creates no Notes
   and no uploads, so those three types have never been rendered with real content.
