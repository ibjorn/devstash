# Paystack Integration Plan

What's built, what's left, and how to finish Pro billing for DevStash: Free-tier
gating, the subscription edge cases still open, and deploying the demo to Vercel.

> Generated by `/research paystack-integration-research` on 2026-10-16.
> Sources: `context/research/paystack-integration-research.md`,
> `context/features/paystack-billing-spec.md`, commit `93d4312`
> (*feat: Paystack Pro subscriptions billed in ZAR*), `prisma/schema.prisma`,
> `src/auth*.ts`, `src/actions/`, `src/app/api/`, `src/lib/`, and Paystack's API
> docs (via Context7, since paystack.com blocks fetches).
>
> The prompt originally came from another repo and was written for Stripe. It has
> since been converted to Paystack, and the translation table below is kept for
> anyone reading Stripe-based material. Checkout, the callback, the webhook and the
> settings UI already shipped in `93d4312` and were confirmed end-to-end in test mode.
> So **Part 1 records what exists** and **Part 2 plans what's left**, including every
> open issue the prompt lists. **This is a design document. Nothing in Part 2 is
> built.**
>
> **DevStash is a demo, not a product.** It's deployed on Vercel but never goes
> live: Paystack stays in **test mode** everywhere, so no real money moves. "Done"
> for DevStash means the demo flow works end to end in test mode (Parts 1–2).
>
> **Part 3 is a production reference** for the real Paystack project that follows
> the course: live keys, activation, legal, refunds, dunning, reconciliation,
> monitoring, a go-live runbook, and invoicing / variable recurring billing /
> inventory (3.7). None of it is planned for DevStash.

## Stripe → Paystack translation

| Prompt (Stripe) | DevStash (Paystack) |
|---|---|
| $8/mo, $72/yr | **R135/mo, R1,200/yr**, charged in ZAR. A South African Paystack account can't charge USD. The UI shows an approximate USD figure from the daily ECB rate. |
| `stripeCustomerId` | `paystackCustomerCode` (`CUS_…`) |
| `stripeSubscriptionId` | `paystackSubscriptionCode` (`SUB_…`) |
| — | `paystackEmailToken`, required to disable a subscription through the API |
| — | `subscriptionStatus` (Paystack's own string), `currentPeriodEnd` |
| Stripe Checkout Session | `POST /transaction/initialize` with a `plan`, then redirect to `authorization_url` |
| `success_url` | `callback_url` → `GET /api/billing/callback?reference=…`, verified server-side |
| Customer Portal | `GET /subscription/:code/manage/link`, a hosted page for card updates and cancelling |
| `STRIPE_WEBHOOK_SECRET` | None. Paystack signs with the **secret key** (HMAC-SHA512, `x-paystack-signature`) |
| `checkout.session.completed` | `charge.success` + `subscription.create` |
| `customer.subscription.updated` | `subscription.not_renew`, `invoice.update` |
| `customer.subscription.deleted` | `subscription.disable` |
| `invoice.payment_failed` | `invoice.payment_failed` (same name) |
| Plan switch via the API | **Not available.** Paystack has no plan swap: cancel, then resubscribe |
| Stripe Dashboard setup | Paystack Dashboard setup (see [Dashboard setup](#paystack-dashboard-setup)) |

### The Stripe-era JWT `isPro` workaround doesn't apply here, so don't port it

The Stripe version of the prompt put `isPro` into the JWT and re-reads it from the database in the
`jwt` callback on every validation. **DevStash should not do this**, for three reasons:

1. **`isPro` isn't in the session at all.** `src/types/next-auth.d.ts` adds only
   `user.id`, and the `session` callback in `src/auth.config.ts` copies only
   `token.sub`. Everything that needs the plan already reads it from the database:
   `getBillingUser()` on `/settings`, and the webhook writes straight to `User`.
   A webhook's change shows up on the very next request. There's no stale-session
   problem to fix.
2. **It would break the proxy.** Callbacks live in `src/auth.config.ts` because that
   config is **edge-safe**. `src/proxy.ts` builds its own NextAuth instance from it,
   and the file's comments say the Prisma adapter can't run on the edge. A
   `prisma.user.findUnique` inside `jwt` would run there too.
3. **Gates must read the database anyway.** A session claim is only a cached copy.
   The security boundary is the server action or route handler, which already does a
   DB round trip and can select `isPro` in the same query (see `getPlanUsage` below).

If a client component ever needs the plan, pass it down as a prop from the server
component that already loaded the user. Don't add it to the token.

### Webhook event map (as built)

| Event | Matched on | Effect |
|---|---|---|
| `charge.success` | customer code, else `metadata.userId` | `isPro = true` (+ customer code) |
| `subscription.create` | customer code; ignored unless the plan is ours | full `subscriptionState()` |
| `subscription.not_renew` | subscription code | status `non-renewing`, **still Pro** |
| `subscription.disable` | subscription code | `isPro = false`, status `complete`/`completed`/`cancelled` |
| `invoice.update` (paid) | subscription code | `isPro = true`, `active`, new period end |
| `invoice.payment_failed` | subscription code | status `attention`, Pro kept (no dunning) |
| anything else | — | `200`, ignored |

Lifecycle events match on the **subscription** code, so a late event for an old
subscription can't touch a newer one.

### Auth & data access patterns the remaining work must follow

- **Session:** JWT strategy. `session.user.id` comes from `token.sub`, and nothing else
  is added.
- **Server actions:** `getSessionUserId()` (`src/lib/db/session-user.ts`) returns
  `null` when signed out, and the action answers `{ success: false, error }`. It never
  throws.
- **Server components:** `requireUserId()` is cached per request and throws if called
  unprotected.
- **Route handlers:** `/api/*` isn't in the proxy matcher, so each route calls
  `auth()` itself (see `api/items/upload`).
- **Results:** `{ success, data?, error?, fieldErrors? }`. `error` is toasted.
- **Env flags:** a literal `"true"` turns a flag on. Anything else is off
  (`SKIP_EMAIL_VERIFICATION` is the precedent).
- **Tests:** colocated `*.test.ts`. Mock `@/lib/prisma`, `@/auth`,
  `@/lib/db/session-user`, `@/lib/rate-limit` and `fetch`. `vi.hoisted()` +
  `vi.resetAllMocks()`.

### Known open issues (from feature history + this review)

1. ✅ **Mostly resolved (2026-10-17):** `/settings` now re-reads a live
   subscription from Paystack on each view (`refreshSubscription`), so a cancellation
   or ending shows up without a webhook; `hasProAccess()`'s 24-hour grace covers a
   user who never opens settings. *Originally:* **A missed `subscription.disable` leaves the user Pro forever.** Nothing re-checks
   a `non-renewing` user whose `currentPeriodEnd` has passed. **In the demo this is
   the most visible bug**: running locally there's usually no tunnel, so cancellation
   webhooks *never* arrive. On Vercel, test mode retries a failed webhook hourly for
   10 hours, then gives up.
2. ✅ **Resolved (2026-10-17):** the demo is live and smoke-tested on Vercel.
   *Originally:* **The Vercel demo isn't wired for billing yet:** production migration, test keys
   and plan codes in Vercel, `APP_URL`, and the test webhook URL.
3. ✅ **Resolved (2026-10-16):** `deleteAccount` now disables an `active` or
   `attention` subscription before deleting anything, and aborts the deletion if
   Paystack refuses. `non-renewing` is skipped because it's already cancelled on
   Paystack's side and a second disable could fail and block the deletion for
   nothing. *Originally:* deletion removed the `User` row and left the
   subscription running on Paystack.
4. ✅ **Resolved (2026-10-17):** a `non-renewing` user can resubscribe on either
   plan; the new subscription's first charge waits for the old period to end.
   Paystack refuses `POST /subscription/enable` on a cancelled subscription
   ("cannot be reactivated"), so it's always a new one. Unit-tested; the
   `start_date` call itself is not yet confirmed in Paystack test mode. *Originally:* **No plan
   switching** — a monthly subscriber who cancelled to go yearly had to wait out the
   period.

## Part 2: Implementation plan for what's left

### Design decisions

- **One switch:** `BILLING_ENFORCED="true"` turns every gate on at once. It's off by
  default, so everyone gets everything, as the project overview asks. Turn it on in
  Vercel (or `.env`) to show the Free-tier wall and the upgrade flow. While it's off
  the gates still run their logic but always allow, so the code paths stay exercised.
- **Gates live server-side, in actions and routes.** The UI hides or locks controls
  for courtesy, but that isn't a control.
- **One query per gate:** `isPro`, status, period end and both counts come from a
  single `findUnique` with `_count`.
- **Effective Pro ≠ `isPro`.** `hasProAccess()` also expires a `non-renewing` user
  past `currentPeriodEnd` (+ 1 day grace), which closes open issue 1 without a cron.
- **Downgrade keeps data.** A user over a limit, or holding File/Image items, keeps
  reading, editing, downloading and deleting them. Only *new* creation is blocked.
- **Count-then-create isn't atomic.** Two parallel creates at 49 can land 51. That's
  acceptable for a soft product limit. Not worth serializable transactions.

### Files to create

#### 1. `src/lib/entitlements.ts`: pure logic, no I/O

```ts
import { PRO_TYPE_NAMES } from "@/lib/db/item-types"; // or move the Set here — see note

export const FREE_LIMITS = { items: 50, collections: 3 } as const;

// Grace past currentPeriodEnd before a non-renewing user loses Pro, in case
// Paystack's subscription.disable is late or never arrives.
const EXPIRY_GRACE_MS = 24 * 60 * 60 * 1000;

/** Only a literal "true" — a typo must never switch gating on in a way nobody expects. */
export function isBillingEnforced(): boolean {
  return process.env.BILLING_ENFORCED === "true";
}

export interface PlanUsage {
  isPro: boolean;
  subscriptionStatus: string | null;
  currentPeriodEnd: Date | null;
  items: number;
  collections: number;
}

export function hasProAccess(plan: PlanUsage, now = new Date()): boolean {
  if (!plan.isPro) return false;
  if (plan.subscriptionStatus !== "non-renewing" || !plan.currentPeriodEnd) {
    return true;
  }
  return now.getTime() < plan.currentPeriodEnd.getTime() + EXPIRY_GRACE_MS;
}

export type Denial = "ITEM_LIMIT" | "COLLECTION_LIMIT" | "PRO_TYPE";

export const DENIAL_MESSAGES: Record<Denial, string> = {
  ITEM_LIMIT: `Free accounts hold up to ${FREE_LIMITS.items} items. Upgrade to Pro for unlimited.`,
  COLLECTION_LIMIT: `Free accounts have up to ${FREE_LIMITS.collections} collections. Upgrade to Pro for unlimited.`,
  PRO_TYPE: "File and image items are a Pro feature.",
};

export function checkItemCreate(plan: PlanUsage, typeName: string): Denial | null {
  if (!isBillingEnforced() || hasProAccess(plan)) return null;
  if (PRO_TYPE_NAMES.has(typeName)) return "PRO_TYPE";
  return plan.items >= FREE_LIMITS.items ? "ITEM_LIMIT" : null;
}

export function checkCollectionCreate(plan: PlanUsage): Denial | null {
  if (!isBillingEnforced() || hasProAccess(plan)) return null;
  return plan.collections >= FREE_LIMITS.collections ? "COLLECTION_LIMIT" : null;
}

/** For AI, export and custom types once they exist. */
export function checkProFeature(plan: PlanUsage): boolean {
  return !isBillingEnforced() || hasProAccess(plan);
}
```

> **Note:** `PRO_TYPE_NAMES` is currently a module-private `const` in
> `src/lib/db/item-types.ts`. Move it to `src/lib/system-types.ts` (import-free,
> already the source of truth for the seed) and import it from both places, so pure
> code doesn't pull in Prisma.

#### 2. `src/lib/db/entitlements.ts`: the one query

```ts
import { prisma } from "@/lib/prisma";
import type { PlanUsage } from "@/lib/entitlements";

// Null on a stale session, as getBillingUser documents
export async function getPlanUsage(userId: string): Promise<PlanUsage | null> {
  const user = await prisma.user.findUnique({
    where: { id: userId },
    select: {
      isPro: true,
      subscriptionStatus: true,
      currentPeriodEnd: true,
      _count: { select: { items: true, collections: true } },
    },
  });
  if (!user) return null;

  const { _count, ...plan } = user;
  return { ...plan, items: _count.items, collections: _count.collections };
}
```

#### 3. `src/lib/entitlements.test.ts`

- `isBillingEnforced`: `"true"` only. `"TRUE"`, `"1"` and unset → false.
- Not enforced → every check returns `null` / `true`, even at 50 items, even for File.
- Enforced, Free: 49 items allowed, 50 → `ITEM_LIMIT`. File/Image → `PRO_TYPE`
  regardless of count. 2 collections allowed, 3 → `COLLECTION_LIMIT`.
- Enforced, Pro: unlimited.
- `hasProAccess`: active → true. Non-renewing before the end → true. Within grace →
  true. Past grace → false. `isPro: false` → false regardless of status.

### Files to modify

#### `src/lib/paystack.ts`: add `disableSubscription`

```ts
/** Stops future charges. Needs the email token Paystack issued with the subscription. */
export function disableSubscription(code: string, token: string) {
  return paystackRequest("/subscription/disable", z.unknown(), {
    method: "POST",
    body: { code, token },
  });
}
```

Confirmed against Paystack's API reference: `POST /subscription/disable`,
body `{ code, token }`, response `{ status: true, message }` with no `data`. If
`envelopeSchema`'s `data: z.unknown()` rejects a missing key, make it `.optional()`.

#### `src/lib/billing.ts` → `billingState()`: show expired Pro as Free

This applies whether or not gating is enforced, because it's the only place the
missed-disable fix becomes visible while `BILLING_ENFORCED` is off. `billingState()`
takes `currentPeriodEnd` as well (`getBillingUser` already selects it) and returns
`"free"` when `hasProAccess()` says the period has run out:

```ts
export function billingState(user: {
  isPro: boolean;
  paystackSubscriptionCode: string | null;
  subscriptionStatus: string | null;
  currentPeriodEnd: Date | null;
}, now = new Date()): BillingState {
  if (!hasProAccess({ ...user, items: 0, collections: 0 }, now)) return "free";
  // …rest unchanged
}
```

(If spreading dummy counts reads badly, give `hasProAccess` a narrower parameter
type with just `isPro`, `subscriptionStatus` and `currentPeriodEnd`. That's cleaner,
and `PlanUsage` still satisfies it.) An expired user then sees the upgrade buttons
again. `startCheckout` must agree. Today it refuses while `user.isPro` is set *or* the
status is live, and `non-renewing` counts as live. So an expired user is refused on
both counts. It should refuse only while `hasProAccess()` is true, or while the
status is `active` / `attention`, since those can still charge. That lets an
expired non-renewing user resubscribe. The old subscription won't charge again. Tests: expired
non-renewing → `"free"`; within grace → `"non-renewing"`; `startCheckout` allows an
expired user.

#### `src/actions/profile.ts` → `deleteAccount`: cancel before deleting (open issue 3)

Select the billing columns with the email. Before the transaction:

```ts
// Cancel first: once the row is gone nothing links this person to the
// subscription, and Paystack would keep charging them
if (
  user.paystackSubscriptionCode &&
  user.paystackEmailToken &&
  isLiveSubscriptionStatus(user.subscriptionStatus)

  try {
    await disableSubscription(user.paystackSubscriptionCode, user.paystackEmailToken);
```

row, so `updateBilling` returns `0`, which is harmless.

of scope.

Tests (`profile.test.ts`): a live subscription → disable called with code + token

### Paystack test-mode setup

**Done and verified locally.** For reference (from the billing spec):

1. Test mode → Settings → API Keys & Webhooks → `sk_test_…` into `.env`.
2. Plans: **Pro Monthly** R135 `monthly`, **Pro Yearly** R1,200 `annually` → plan
   codes into `.env`. Optional: an **hourly** throwaway plan to watch renewals fire.
3. Webhooks need a public URL. Use `cloudflared tunnel --url http://localhost:3000`
   (or ngrok) → set the **test** webhook URL to `https://<tunnel>/api/webhooks/paystack`.
   The callback route covers basic checkout without it.
   Alternative (not yet tried here): Paystack's official CLI has `webhook listen`
   to forward test events to localhost and `webhook ping --event <name>` to send
   samples. The syntax, whether it rewrites the test webhook URL, and whether it's
   still maintained are all unverified, so check `--help` first. Sample pings
   carry no real customer or subscription codes, so they test signatures, not
   billing state. Sources: [Paystack blog](https://paystack.com/blog/product/cli),
   [third-party guide](https://mctaba.com/learn/paystack/debugging-paystack-with-the-paystack-cli).

### Vercel demo deployment (still test mode)

> The full step-by-step setup and the demo walkthrough live in
> [how-to-demo.md](how-to-demo.md). This section keeps the billing-specific notes.

The demo runs on Vercel with the **same Paystack test account** as local dev.
Nothing here involves live keys. Each step is done deliberately by Björn.

1. **Production database:** `npm run db:deploy` applies
   `20261015120000_paystack_billing` to the demo's production database. Per project
   rules this is an explicit, confirmed, production-only action. Check `db:status`
   first.
2. **Vercel env vars:** the same `PAYSTACK_SECRET_KEY` (`sk_test_…`) and the same
   `PAYSTACK_PLAN_CODE_MONTHLY` / `_YEARLY` as `.env`. One test account means the
   same plans. Also set `APP_URL=https://<vercel-domain>`: it builds the
   `callback_url`, and a wrong value sends people back to localhost after checkout.
3. **Test webhook URL → Vercel:** `https://<vercel-domain>/api/webhooks/paystack`.
   **Watch for this:** as far as I know, Paystack holds **one webhook URL per mode**,
   and local dev and Vercel share test mode. Pointing it at Vercel means local dev
   gets no webhooks. That's fine: the callback route covers checkout, and
   `hasProAccess()` covers cancellations that never arrive. Point it at a tunnel
   only while you're testing webhooks locally, then switch it back.
4. **Cross-traffic is harmless:** a webhook for a user who only exists in the local
   database matches no row on Vercel. `updateBilling` returns `0` and nothing changes.
5. **Gating:** `BILLING_ENFORCED` stays unset unless you want the demo to show the
   Free-tier wall.
6. **Smoke test with Paystack test cards:** subscribe, check the webhook was delivered
   (Paystack dashboard → webhook logs), cancel via the manage link, then confirm
   `non-renewing` in settings.

## Part 3: Production reference (for a real integration, not DevStash)

DevStash stops at Part 2. **This part is for the real Paystack project that follows
the course.** It covers what a production integration needs that a test-mode demo
can skip. The DevStash code in Parts 1–2 is the starting point; this is the gap
between it and production.

**How sure each claim is:**
- ✅ **Verified** against Paystack's API docs (via Context7, 2026-10-16). Still
  re-check before relying on it, since docs change.
- ⚠️ **Unverified**: from general knowledge or inference. Confirm with Paystack
  support, the dashboard, or a professional before relying on it.

### 3.1 Accounts, keys and environments

- ✅ Test and live are separate environments with **separate keys**: `pk_test_` /
  `sk_test_` and `pk_live_` / `sk_live_`. Plans, customers and subscriptions don't
  carry over, so **live plan codes differ from test ones**. Recreate the plans in live
  mode and set the env vars per environment.
- ✅ Test mode doesn't process settlements, and some payment channels are
  unavailable. Some flows can only be seen working for real in live mode.
- ⚠️ There seems to be **one webhook URL per mode** per account. Dev, staging and any
  preview deployments all share test mode, so only one of them gets webhooks at a
  time. Options, roughly in order of effort:
  1. Point test webhooks at staging. Dev relies on the callback route plus
     reconciliation (3.4).
  2. A small webhook relay that verifies the signature and forwards events to each
     environment.
  3. A second Paystack account for staging. Check whether Paystack allows this for
     one business.
- ⚠️ **Rotating the secret key also changes the webhook signing key**, since the
  signature is HMAC'd with it. A rotation has to update the env var and redeploy in
  one step, or webhooks start failing with `401`. Live mode retries for 72 h (✅), so
  a short gap recovers by itself.
- ✅ **`APP_URL` per environment.** It builds `callback_url`. Wrong in production means
  paying customers land on localhost or staging after checkout.

### 3.2 Business and legal prerequisites (all ⚠️, start these early)

These have lead time the code doesn't. Start them in parallel with development.

| Prerequisite | Why | Check with |
|---|---|---|
| **Account activation / compliance**: business registration, director identity, payout bank account | Live keys normally only work on an activated account, and review can take days. | Paystack dashboard compliance section, Paystack support |
| **Terms of service, privacy policy, refund and cancellation policy, contact details** on the site | Payment providers usually require them before activation. South African law also applies: **POPIA** covers personal information, and the **ECT Act** sets disclosure duties for online sellers. | Paystack's activation checklist; a lawyer for the wording |

| **Fees** | Paystack takes a fee per transaction. Price with it in mind. Card and currency mix can change the effective fee. | Paystack's pricing page |

### 3.3 Subscription lifecycle: what the demo leaves open

**Account deletion must cancel first.** This is Part 2's `deleteAccount` change, and
in production it's **priority one**: without it, a deleted user keeps being charged
by a business that no longer knows who they are.

**Changing a price: the trap.** ✅ `PUT /plan/:code` takes
`update_existing_subscriptions`, and it **defaults to `true`**. Changing the amount
without passing `false` moves **every existing subscriber** to the new price from
their next billing cycle. To grandfather existing customers:

```ts
// Never update a live plan's amount without saying what happens to existing
// subscribers — Paystack's default applies it to all of them.
await paystackRequest(`/plan/${encodeURIComponent(planCode)}`, z.unknown(), {
  method: "PUT",
  body: { amount: newSubunit, update_existing_subscriptions: false },
});
```

Often it's cleaner to **create a new plan** for a new price and point the env var
at it. Old subscribers stay on the old plan, and `billingForPlanCode` must then
recognise both codes.

**Plan switching (monthly ↔ yearly).** Paystack has no plan swap or proration. ✅
`POST /subscription` accepts `customer`, `plan`, `authorization` and **`start_date`**,
and the customer must already have an authorization from an earlier transaction. So a
switch that takes effect at the end of the current period:

```ts
// Order matters. Create and store the new subscription first, then disable the
// old one. The old one's subscription.disable webhook then matches no row
// (lookups go by subscription code), so it can't revoke Pro mid-switch.
const next = await createSubscription({
  customer: user.paystackCustomerCode,
  plan: planCodeFor(target),
  start_date: user.currentPeriodEnd.toISOString(), // no double charge this period
});
await updateBilling({ id: userId }, subscriptionState(next));
await disableSubscription(oldCode, oldEmailToken);
```

⚠️ Check in test mode which status a subscription with a future `start_date`
reports, and whether `subscriptionState()` treats it as Pro. Also check what Paystack
returns as `email_token` on create.

**Failed renewals and dunning.** Today `invoice.payment_failed` sets `attention` and
keeps Pro. In production:
- Email the customer with the manage link to update their card. The link is
  short-lived, so link to `/settings#billing`, which fetches it fresh.
- ⚠️ Decide how long `attention` keeps Pro. Paystack eventually sends
  `subscription.disable` if its retries fail, but confirm its retry schedule for
  subscription charges.
- ✅ `subscription.expiring_cards` arrives at the **start of each month** listing
  subscriptions whose card expires that month. Use it to warn customers *before* a
  renewal fails. Note that its `data` is an **array**, unlike the other events.
- ✅ `invoice.create` arrives about **3 days before** a renewal is due. It's a hook
  for "renewing soon" emails, if you want them.

**Refunds.** ✅ `POST /refund` takes `{ transaction, amount?, customer_note?,
merchant_note? }`. Leaving out `amount` gives a full refund, and a partial refund
can't exceed the original. Status arrives as webhooks: `refund.pending`,
`refund.processing`, `refund.processed`, `refund.failed` (the refund amount is
credited back to your balance) and `refund.needs-attention`. Decide whether a refund
also cancels the subscription and revokes Pro. Paystack won't do that for you.

**Disputes (chargebacks).** ✅ `charge.dispute.create` / `.remind` / `.resolve`.
At minimum, log them and alert someone, since they have response deadlines. Whether
to suspend Pro during a dispute is a business decision.

**Customer email changes.** ⚠️ A Paystack customer is keyed by email. If the app
lets users change their email, the Paystack customer keeps the old one, so receipts
and manage-link emails go to the old address. Either update the Paystack customer
(`PUT /customer/:code`) when the email changes, or decide you don't care.

### 3.4 Reliability: don't trust webhooks alone

DevStash's `hasProAccess()` grace check is a demo-grade patch for missed webhooks.
In production, **reconcile on a schedule**: re-read every live subscription from
Paystack and correct the database. This catches any missed event, not just
`subscription.disable`, including ones lost beyond the 72-hour retry window (✅).

```ts
// src/app/api/cron/reconcile-billing/route.ts — run daily (Vercel Cron)
export async function GET(request: Request) {
  // Vercel Cron sends Authorization: Bearer $CRON_SECRET
  if (request.headers.get("authorization") !== `Bearer ${process.env.CRON_SECRET}`) {
    return NextResponse.json({ ok: false }, { status: 401 });
  }

  const users = await prisma.user.findMany({
    where: { paystackSubscriptionCode: { not: null }, isPro: true },
    select: { id: true, paystackSubscriptionCode: true },
  });

  let corrected = 0;
  for (const user of users) {
    try {
      const sub = await fetchSubscription(user.paystackSubscriptionCode!);
      corrected += await updateBilling({ id: user.id }, subscriptionState(sub));
    } catch (error) {
      console.error("Reconcile failed for %s", user.id, error); // keep going
    }
  }
  return NextResponse.json({ ok: true, checked: users.length, corrected });
}
```

Needs `fetchSubscription(code)` (`GET /subscription/:code`) added to
`src/lib/paystack.ts`. ⚠️ Paystack's API rate limits aren't documented here.
Beyond a few hundred subscribers, batch or spread the calls. `updateBilling` writes
even when nothing changed, which is harmless, but count real differences if you want
an accurate `corrected`.

**Log every webhook.** A `BillingEvent` table (event type, Paystack reference or
subscription code, a hash of the raw body, received/processed timestamps, outcome)
gives you an audit trail and a way to replay events. ⚠️ Paystack payloads don't
obviously carry a unique event id, so dedupe on the body hash.

```prisma
model BillingEvent {
  id          String   @id @default(cuid())
  event       String
  bodyHash    String   @unique // sha256 of the raw body — replay/dedupe key
  reference   String?  // transaction reference or SUB_ code
  outcome     String   // handled | ignored | failed
  receivedAt  DateTime @default(now())
}
```

**Monitoring.** Alert on: webhook `401`s (a key or URL is wrong), webhook `500`s (the
database is failing, and Paystack is retrying), reconciliation corrections above zero
(webhooks are being missed), and any `charge.dispute.*`. Logs alone won't wake anyone
up.

**Security notes that carry over unchanged:** signature verified on the raw body
before parsing, constant-time compare, and the `metadata.userId === session user`
check in the callback. Redirect checkout keeps card data off your servers entirely.
Don't log full webhook payloads in production: they contain customer emails and
card metadata, which is personal information under POPIA.

### 3.7 Beyond SaaS subscriptions: invoicing, variable recurring billing, inventory

The follow-on project has **inventory, client invoicing and recurring billing**.
DevStash only does one thing: a fixed-price plan per user. A business system needs
several Paystack tools, and the app has to own far more of the bookkeeping.

#### Pick the right Paystack tool per payment shape

| Payment shape | Paystack tool | Who schedules and retries |
|---|---|---|
| **Fixed amount on a fixed interval** (SaaS plan, fixed retainer) | ✅ **Subscriptions**: plans + `subscription.*` events (what DevStash uses) | Paystack charges and retries |
| **Variable amount on a schedule** (monthly invoice total, usage, instalments) | ✅ **Recurring charges**: save the card from a first payment, then `POST /transaction/charge_authorization` with any amount | **You.** Your cron charges, and you handle failures and retries ⚠️ |
| **Client pays an invoice when ready** | ✅ **Payment Requests** (`POST /paymentrequest`): line items, tax, due date, Paystack-hosted invoice page and email | The client pays. You chase overdue ones |
| **One-off payment link** | ✅ `POST /transaction/initialize` (same as DevStash's checkout) | The client pays |
| **Bank debit order instead of a card** | ✅ Direct debit exists (`channel: "direct_debit"`, and a charge comes back `processing`, not `success`) | ⚠️ Confirm it's offered to South African merchants |

#### Recurring charges (`charge_authorization`), verified details

- ✅ After the first successful transaction, `verifyTransaction` returns
  `data.authorization`. **Store `authorization_code`, but only when
  `reusable: true`.** Also store `last4`, `exp_month`/`exp_year`, `brand` and
  `signature`. Paystack issues a new authorization code each time the card is used,
  but the `signature` stays the same for the card, so use it to dedupe saved cards.
- ✅ Charge with `{ email, amount, authorization_code, reference?, metadata?, queue? }`.
  `amount` is in the subunit. Send `queue: true` for scheduled batch runs.
- ✅ A direct-debit charge returns `status: "processing"`. **Never treat the
  response as final.** Settle the invoice only on `charge.success` (or after
  verifying the reference).
- **Use your invoice id as the `reference`** (✅ only `-`, `.`, `=` and alphanumerics
  are allowed). ⚠️ If Paystack rejects a reused reference, as payment providers
  usually do, a retried cron run can't double-charge the same invoice attempt.
  Verify this in test mode before relying on it. Otherwise keep your own
  "charge attempted" row per invoice attempt.
- ⚠️ Retries and dunning are yours with this approach. Paystack's subscription
  retries don't apply. Warn clients about expiring cards from the stored
  `exp_month`/`exp_year`.

#### Payment Requests (invoices), verified details

- ✅ `POST /paymentrequest` takes `customer` (code or id), `line_items`
  (`[{ name, amount, quantity }]`), `tax` (`[{ name, amount }]`), `due_date`,
  `description`, `metadata`, `send_notification`, `draft` and `invoice_number`.
  It returns a `request_code` (`PRQ_…`), `status`, `paid` and `pending_amount`.
  Finalizing a draft can return a `pdf_url`.
- ✅ **`currency` defaults to `NGN`.** Always pass `currency: "ZAR"`. Missing it is
  exactly the kind of bug that only shows up on a real invoice.
- ✅ **`send_notification` defaults to `true`.** Paystack emails the client on
  create. Pass `draft: true` (or `send_notification: false`) to review first, then
  `POST /paymentrequest/finalize/:code` and `/paymentrequest/notify/:code`.
- ✅ Events: `paymentrequest.pending` (created), `paymentrequest.success` (paid), and
  `invoice.payment_failed`. **A paid invoice *also* fires `charge.success`**, so
  handle the payment in one place, not both.
- ⚠️ `invoice_number` auto-increments per Paystack account, and the PDF is
  Paystack's. If South African tax invoices need your own sequential numbering and
  VAT details, which the accountant should confirm, **your app is the invoice
  system** and Paystack is only how clients pay. Don't let Paystack's numbering
  become your legal sequence by accident.

#### Webhook routing: the DevStash handler doesn't carry over as-is

DevStash's `onChargeSuccess` grants Pro for **any** `charge.success` from a known
customer. In an app that also takes invoice payments, **paying an invoice would grant
a subscription.** Tag every transaction you start with what it's for, and route on
that:

```ts
// Every initialize / charge_authorization / payment request carries this
type PaymentPurpose =
  | { kind: "subscription"; userId: string }
  | { kind: "invoice"; invoiceId: string }
  | { kind: "order"; orderId: string };

async function onChargeSuccess(data: unknown) {
  const charge = chargeSchema.parse(data);
  const purpose = parsePurpose(charge.metadata); // Zod, like metadataUserId
  if (!purpose) return logUnroutable(charge);    // don't guess — alert instead

  switch (purpose.kind) {
    case "subscription": return grantSubscription(purpose.userId, charge);
    case "invoice":      return settleInvoice(purpose.invoiceId, charge);
    case "order":        return settleOrder(purpose.orderId, charge);
  }
}
```

Settling must be idempotent, like DevStash's absolute sets: "mark invoice
`INV-0042` paid by reference `X`" is safe to repeat. "Add R500 to the balance" is not.

#### The app owns the ledger, Paystack moves money

- **Invoices, line items, credit notes and balances live in your database**, with
  Paystack references stored against them (`reference`, `request_code`,
  `authorization_code`). Paystack is the payment rail, not the record.
- **Money as integer cents everywhere** (Paystack's subunit). No floats, and round
  once, where tax is calculated.
- **Reconcile payments against invoices daily**, not just subscriptions (3.4). List
  the day's Paystack transactions and match each one to an invoice or order. Anything
  unmatched gets flagged for a person.
- **Partial payments and overpayments:** ⚠️ `pending_amount` on payment requests
  suggests partial payment is possible. Decide how invoices handle it before a client
  does it.
- **Refunds become credit notes:** a refund (3.3) against an invoice should create a
  credit note in your system, not just a Paystack record.

#### Inventory and payments

Paystack knows nothing about stock. Its `line_items` are display text. The rules
that matter:

- **Decide when stock is committed:** when the invoice or order is issued (a
  reservation), or when payment lands. Reservations need an expiry that releases
  stock for unpaid invoices.
- **Webhook-driven stock changes must be idempotent.** A retried `charge.success`
  must not decrement stock twice. Key the decrement on the payment reference (a
  unique constraint) rather than doing it blind.
- **Payment after stock ran out:** with reserve-on-payment, two clients can pay for
  the last unit. Decide in advance: backorder, refund, or reserve at checkout.
- **Refunds and returns:** a refund doesn't put stock back. A return does. Keep them
  as separate actions.
