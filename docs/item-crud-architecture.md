# Item CRUD Architecture

A design for creating, reading, updating and deleting items across all seven types,
using **one** action file, **one** dynamic route, and shared components that adapt by
type.

> Generated by `/research item-crud-research` on 2026-08-26. **Design document — nothing
> here is built.** Sources: `context/project-overview.md`, `docs/item-types.md`,
> `prisma/schema.prisma`, and the existing `src/actions/`, `src/lib/db/`,
> `src/components/` patterns this follows.
>
> Two prompt sources don't exist: `docs/content-types.md` (the type reference is at
> **`docs/item-types.md`**) and `src/lib/constants.tsx` (type constants live in
> `prisma/seed.ts`, `src/lib/type-icons.ts` and `src/lib/db/items.ts`).

---

## The organising principle

**Types differ in how content is edited and displayed, not in how it is stored or
mutated.** All seven are rows in one `Item` table with one owner, one type FK, the same
favourite/pin flags, the same collection and tag joins. A Snippet and a Link differ by
which of `content` / `url` / `fileUrl` they populate — and by which editor and viewer a
human needs.

So the split is:

| Layer | Type-aware? |
|---|---|
| `src/actions/items.ts` — mutations | **No.** One create, one update, one delete. |
| `src/lib/db/items.ts` — queries | **No.** Type is a `where` filter, not a code path. |
| `src/lib/validation/items.ts` — schemas | **Partly.** One discriminated union on `contentType`. |
| `src/components/items/*` — editors & viewers | **Yes.** This is where every branch lives. |

The action's job is: authenticate, validate, check ownership, write, revalidate. None of
that changes because the type is Prompt instead of Command. Pushing type branches into
the action would mean seven near-identical mutations drifting apart, and would put the
"what does a Snippet look like" decision in a file that can't render anything.

## Routing: `/items/[type]`

### The URL the sidebar already emits

`AppSidebar` builds `href = /items/${type.slug}` where the slug is the type name
pluralised and lowercased (`Snippet` → `snippets`). Those links **currently 404** — no
`src/app/items/` route exists. This design fills exactly that hole, with one caveat
below.

### Route placement — put it under `/dashboard`

The sidebar's `href` is `/items/{slug}`, but the file should live at
`src/app/dashboard/items/[type]/page.tsx`, making the real URL `/dashboard/items/snippets`
(and `AppSidebar`'s template updated to match). Two reasons:

1. **Auth.** `src/proxy.ts` matches `["/dashboard/:path*", "/profile/:path*"]`. A
   top-level `/items` would be **completely unauthenticated** — the exact trap `/profile`
   fell into and had to be patched for. Nesting under `/dashboard` inherits protection
   with no matcher change.
2. **Chrome.** `src/app/dashboard/layout.tsx` already wraps children in `AppShell`
   (sidebar, top bar, stale-JWT guard). A nested route gets all of it free; a sibling
   route tree would need its own layout, and the piece most likely to be dropped from a
   hand-copied layout is `AppShell`'s `redirect("/api/auth/session-expired")`.

If the bare `/items/*` URL is wanted for its own sake, the alternative is a `(app)` route
group plus adding `"/items/:path*"` to the proxy matcher — more surface, same result.
Either way, **the matcher and the route must be decided together**; that pairing is the
one real security decision in this design.

### Resolving the slug to a type row

The `[type]` segment is a plural lowercase slug; the DB stores singular
`ItemType.name`. Resolution belongs in `src/lib/db/item-types.ts`:

```ts
// /dashboard/items/snippets -> the Snippet ItemType row
export async function findItemTypeBySlug(
  userId: string,
  slug: string,
): Promise<ItemTypeRef | null>
```

Three things it has to get right:

- **De-pluralise by matching, not by string surgery.** Load the candidate types and
  compare `` `${name}s`.toLowerCase() `` to the slug. Stripping a trailing `s` breaks the
  moment a custom type is named "Progress" or "CSS".
- **Custom types are in scope.** Match `WHERE isSystem = true OR userId = :userId`, so a
  user's own type resolves and another user's never does.
- **`findFirst`, not `findUnique`.** `@@unique([userId, name])` is useless for system
  types because Postgres treats NULLs as distinct — `prisma/seed.ts` documents this same
  trap.

A miss calls `notFound()`. The page then renders items filtered to that one type.

### Item detail — a drawer, not a route

The project overview is explicit: item detail "opens in a quick-access **drawer** (not a
full page navigation)". So there is **no `/items/[type]/[id]` page**. Selection is a
search param on the listing route — `?item={id}` — which keeps the drawer linkable,
back-button-correct and server-rendered, without a navigation that discards the list.

## Data fetching (`src/lib/db/items.ts`)

Called **directly from server components**, never from client components, matching every
existing page. New functions alongside the three that exist:

```ts
getItemsByType(userId, itemTypeId, options?): Promise<ItemSummary[]>
getItemById(userId, itemId): Promise<ItemDetail | null>
countItemsByType(userId, itemTypeId): Promise<number>
```

Non-negotiables carried over from the User-Scoped Data feature:

- **`userId` is a required first parameter**, never resolved inside the function. That was
  a deliberate call: resolving internally keeps call sites tidy but makes a forgotten
  scope a silent leak of everyone's rows; a required parameter makes it a compile error.
- **Filter on the indexed `userId` column directly**, not through the `user` relation.
  `Item` has `@@index([userId])` and `@@index([itemTypeId])` — a `WHERE userId AND
  itemTypeId` query hits both.
- **Ownership lives in the `where`, not in a follow-up check.** `getItemById` filters
  `{ id, userId }`, so another user's id returns `null` and becomes a 404 rather than a
  403 — which also declines to confirm the id exists.

`ItemSummary` already exists and is what `ItemRow` consumes. `ItemDetail` extends it with
the payload columns the drawer needs — `contentType`, `content`, `url`, `fileUrl`,
`fileName`, `fileSize`, `language`, `description`, `collections`, `updatedAt`.

## Mutations (`src/actions/items.ts`)

Server Actions, not API routes. The coding standards reserve API routes for webhooks,
upload progress, long-running work, specific status codes, and future mobile/CLI clients;
item CRUD is none of those. **The one exception is file upload** for File/Image, which
wants progress tracking and belongs in a route handler — the action then only records the
resulting R2 URL.

Return the established shape, identical to `src/actions/profile.ts`:

```ts
export interface ItemActionResult {
  success: boolean;
  error?: string;
  fieldErrors?: Record<string, string>;   // keyed by input name
  itemId?: string;                        // create returns the new id
}
```

`fieldErrors` renders next to the offending input; `error` gets toasted. Reuse the
first-message-per-field `toFieldErrors(ZodError)` helper from `profile.ts` — worth
lifting into a shared module rather than copying a third time.

Every mutation follows the same five steps:

```ts
export async function updateItem(formData: FormData): Promise<ItemActionResult> {
  const parsed = itemSchema.safeParse(...);          // 1. validate
  if (!parsed.success) return toFieldErrors(parsed.error);
  try {
    const userId = await requireUserId();            // 2. authenticate
    const result = await prisma.item.updateMany({    // 3. write, scoped
      where: { id: parsed.data.id, userId },         //    ownership in the WHERE
      data: { ... },
    });
    if (result.count === 0) {
      return { success: false, error: "That item no longer exists." };
    }
    revalidatePath("/dashboard", "layout");          // 4. revalidate
    return { success: true };                        // 5. report
  } catch (error) {
    console.error("Update item failed:", error);
    return { success: false, error: "Could not save your changes" };
  }
}
```

**`updateMany`/`deleteMany` with `userId` in the `where`** is the pattern that matters:
it makes the ownership check and the write one atomic statement, so there is no
read-then-write window and no way to forget the second check.

### Ownership isn't only the item

Three foreign keys need validating, and only the first is obvious:

1. **The item** — `where: { id, userId }`, as above.
2. **The item type** — a create/update carries `itemTypeId` from a form the user
   controls. It must be a system type or one of *theirs*, or a user can file items under
   someone else's custom type. Same predicate `findItemTypeBySlug` uses.
3. **Collections** — `ItemCollection` rows link an item to a collection with no ownership
   check of its own. Verify every submitted `collectionId` belongs to `userId` before
   connecting, or a user can attach their item to a stranger's collection.

### Tags

`Tag.name` is globally unique with **no `userId`**. `connectOrCreate` on tag name works
and leaks nothing (tags are only reachable through an item), but it means one user
creating `#internal` hands the row to everyone. **This decision is owed before Item CRUD
ships** — it has been on the backlog since the 2026-07-09 audit, and this is the feature
that forces it. Options: leave global and accept a shared vocabulary; add `userId` +
`@@unique([userId, name])`; or keep the table global and scope only the join. It needs a
migration either way, so decide before writing `createItem`, not after.

### Cache invalidation

`revalidatePath` is currently used **nowhere**, and every data page sets
`export const dynamic = "force-dynamic"`. That kills the full route cache, so a fresh
request always re-queries — but the **client-side Router Cache still serves a stale
listing on a soft navigation** after a mutation. Every mutation therefore needs
`revalidatePath`, and because the sidebar counts live in `AppShell` (a layout), the
create/delete calls need `revalidatePath("/dashboard", "layout")` to refresh them.
Toggling favourite or pin can revalidate the page alone.

Also: **`getItemTypeNavItems` filters `isSystem: true`**, so the sidebar and the profile
breakdown will silently under-count the moment custom types exist — already logged
against the Profile Page feature, and worth fixing in the same pass that makes custom
types reachable.

## Validation (`src/lib/validation/items.ts`)

One schema, discriminated on `contentType`, following `validation/auth.ts` — schemas
shared verbatim between the client form and the server action, so an obvious mistake
costs no round trip while the server stays the real gate.

```ts
const base = z.object({
  title: z.string().trim().min(1, "Title is required").max(200),
  description: z.string().trim().max(500).optional(),
  itemTypeId: z.string().min(1),
  tags: z.array(z.string().trim().min(1).max(50)).max(20).default([]),
  collectionIds: z.array(z.string()).default([]),
});

export const itemSchema = z.discriminatedUnion("contentType", [
  base.extend({
    contentType: z.literal("TEXT"),
    content: z.string().min(1, "Content is required"),
    language: z.string().optional(),
  }),
  base.extend({
    contentType: z.literal("URL"),
    url: z.url("Enter a valid URL"),
  }),
  base.extend({
    contentType: z.literal("FILE"),
    fileUrl: z.url(),
    fileName: z.string().min(1),
    fileSize: z.number().int().positive(),
  }),
]);
```

This is the **only** place type-shape rules belong. `docs/item-types.md` records that all
seven payload columns are nullable with no DB constraint tying `contentType` to the
columns it implies — an item could carry both `content` and `url` and Postgres wouldn't
object. The discriminated union is what actually enforces the convention, so it should
also **null out the columns the branch doesn't own** on update, or a type change leaves
stale content behind.

Note `contentType` is a property of the *item*, not derived from the type row — but the
UI should set it from the chosen type (TEXT for Snippet/Prompt/Command/Note, URL for
Link, FILE for File/Image) rather than letting the user pick, and the action should
re-derive it server-side rather than trusting the field.

## Component responsibilities

### `page.tsx` — server component, no type logic

Resolves the slug, fetches, renders. It is the only place that knows about routing.

```tsx
export const dynamic = "force-dynamic";

export default async function ItemTypePage({ params, searchParams }) {
  const userId = await requireUserId();
  const { type: slug } = await params;
  const itemType = await findItemTypeBySlug(userId, slug);
  if (!itemType) notFound();

  const [items, selected] = await Promise.all([
    getItemsByType(userId, itemType.id),
    itemId ? getItemById(userId, itemId) : null,
  ]);
  // header + ItemGrid + ItemDrawer
}
```

### `ItemGrid` — server, shared

Maps `ItemSummary[]` to the existing `ItemRow`, or an `EmptyState` when empty. `ItemRow`
already draws its border and icon chip from `item.type.color` / `.icon` via
`typeColorTint` and `typeIcons`, so **the list is type-adaptive with no new code**. The
`EmptyState` copy is the one thing that should vary by type ("No snippets yet") — and
unlike the dashboard's deliberately CTA-less empty states, this one **can** carry a
"New snippet" button, because by then the create flow exists.

### `ItemDrawer` — client, shared shell

Owns open/closed, view-vs-edit mode, and submission. Mirrors `ChangePasswordDialog`:
`useState` for pending, client-side `safeParse` first, then the action, then
`fieldErrors` inline and `toast` for everything else. Opening/closing writes `?item=` so
the drawer is linkable and the back button closes it.

**One caution from a real bug:** `DeleteAccountDialog` awaited an action that redirects
and read `result.fieldErrors` off it — but a redirecting server action serialises **no
return value at all**, so `result` was `undefined`, the dereference threw, and the user
got an error toast at the moment the operation succeeded. `deleteItem` should either
return a result and let the client navigate, or redirect and be typed
`ItemActionResult | undefined` with a guard.

### `ItemForm` — client, shared fields + one branch

Renders title, description, tags and collections for every type, then delegates the body
to exactly one editor:

```tsx
{contentType === "TEXT" && <TextEditor language={language} />}
{contentType === "URL"  && <UrlEditor />}
{contentType === "FILE" && <FileUploader />}
```

**This single switch is the type-specific logic for the whole feature.** Three branches,
not seven — File and Image are schema-identical, and the four TEXT types differ only in
placeholder copy and default `language`.

### `editors/*` and `viewers/*` — where types actually diverge

- **`TextEditor`** — Markdown editor for Note, syntax-highlighted code for
  Snippet/Command, plain multi-line for Prompt. Sets `language` (Snippet: a picker;
  Command: default `bash`; Note: `markdown`). *No editor or highlighting library is
  installed yet* — that's a dependency decision this feature has to make.
- **`UrlEditor`** — a single validated URL field.
- **`FileUploader`** — Pro-gated, posts to a route handler for progress, writes back
  `fileUrl` / `fileName` / `fileSize`. `PRO_TYPE_NAMES` in `src/lib/db/items.ts` already
  names File and Image; gating is currently bypassed during development.
- **Viewers** mirror the editors: code block with copy button, link card with
  click-through, image preview vs download link.

### `ItemActions` — client, shared

Favourite, pin, delete. Pure boolean flips on columns every type has — no branching.

## What this design deliberately does not do

- **No per-type action files.** Seven `createSnippet` / `createPrompt` functions would be
  seven copies of the same auth, ownership and revalidation code, drifting apart.
- **No per-type routes.** One `[type]` segment; the type is data.
- **No `/items/[type]/[id]` page.** The spec says drawer.
- **No type-specific queries.** `getItemsByType` takes an `itemTypeId` like any filter.
- **No `contentType` branching in the actions.** The discriminated union has already
  narrowed it by the time the action writes.

## Open questions to settle before implementation

1. **`Tag` scoping** — global vs per-user. Needs a migration; blocks `createItem`.
2. **Route placement** — nest under `/dashboard` (no matcher change) or add
   `"/items/:path*"` to the proxy. **Never ship the route without the matcher.**
3. **Editor dependency** — nothing for Markdown or syntax highlighting is installed.
4. **File uploads** — Cloudflare R2 is unwired. File and Image can ship read-only, or the
   feature can be split so the five TEXT/URL types land first.
5. **Pro gating** — `isPro` exists on `User` and `PRO_TYPE_NAMES` exists in code, but
   nothing enforces either. Free-tier caps (50 items, 3 collections) are unimplemented.
6. **`getItemTypeNavItems`' `isSystem: true` filter** — under-counts once custom types
   are reachable.
