# AI Integration Plan

How to add the four Pro AI features to DevStash: auto-tagging, summaries, "Explain this code"
and the prompt optimizer. It covers which model to use, how the calls are wired, gating,
limits, cost, UI and security.

> Generated by `/research ai-integration-research` on 2026-10-17.
> Sources: `context/research/ai-integration-research.md`, `src/actions/`, `src/app/api/items/upload/route.ts`,

## TL;DR

| Decision | Recommendation |
|---|---|
| Model | **`gpt-6-luna`**, not `gpt-5-nano`. The nano snapshot shuts down on **2026-12-11** (§1) |
| SDK | `openai` v7 with the **Responses API**: `responses.parse` + `zodTextFormat` (Zod 4 is supported) |
| Transport | **Route Handlers under `/api/ai/*`**, not Server Actions, because Next.js runs a client's actions one at a time (§3) |
| Streaming | Stream **Explain** only. Tags, summary and prompt optimization return structured JSON in one response |
| Persistence | **AI endpoints never write to the DB.** They return suggestions, and an accepted suggestion goes into the drawer's form state and is saved by the existing `updateItem` / `createItem` |
| Schema changes | **None.** Summary → `Item.description`, tags → `Item.tags`, optimized prompt → `Item.content`. Explanations are not stored |
| Gating | `checkProFeature(plan)`, the gate uploads already use. A refusal returns 403 with `upgrade: true` |
| Limits | A new `ai` entry in `RATE_LIMITS` that **fails closed**, plus a hard monthly budget on the OpenAI project |
| Cost | Roughly **$0.0004 per tag/summary call** and **$0.002 per explanation**, about R0.007 and R0.04 |

## 1. Model choice — move off `gpt-5-nano`

The project overview specifies `gpt-5-nano`. OpenAI's deprecations page (checked 2026-10-17) says:

| Model | Status | Shutdown | OpenAI's replacement |
|---|---|---|---|
| `gpt-5-nano-2025-08-07` | Deprecated 2026-06-11 | **2026-12-11** | `gpt-5.6-luna` |
| `gpt-5-mini-2025-08-07` | Deprecated 2026-06-11 | 2026-12-11 | `gpt-5.6-terra` |
| `gpt-5.4-nano` | Deprecated 2026-10-01 | 2027-04-01 | `gpt-6-luna` |

The page doesn't list the bare `gpt-5-nano` alias, but that alias resolves to the dated snapshot.
Assume it stops working on the same date, and confirm with `GET /v1/models/gpt-5-nano` (look at
`shutdown_date`). Any code built on nano would need a model migration within eight weeks.

The current models page lists **no nano models at all**. Its efficient tier is **GPT-6 Luna**, described
as "our most efficient model for focused, high-volume tasks":

| | `gpt-5-nano` (retiring) | **`gpt-6-luna`** |
|---|---|---|
| Input / cached / output per 1M tokens | $0.05 / $0.005 / $0.40 | **$0.10 / $0.01 / $0.50** |
| Batch / Flex | 50% off | 50% off |
| Context / max output | — | 1.05M / 128K |
| Knowledge cutoff | 2024 | 2026-05-18 |
| Reasoning effort | minimal…high | **`none`**, low, medium (default), high, xhigh, max |
| Structured outputs, streaming, Responses + Chat Completions | ✅ | ✅ |
| Rate limits (lowest "Build" tier) | — | 5,000 RPM / 2M TPM |

Input costs twice as much and output 25% more. At DevStash's volumes that is a rounding error (§7),
and in exchange you get a model that isn't being retired, has a 2026 knowledge cutoff (it matters for
"explain this code" on recent APIs), and has reasoning effort `none` for the trivial tasks.

`gpt-5.6-luna` is named as nano's replacement on the deprecations page but doesn't appear on the
current models page. Treat it as superseded by `gpt-6-luna`.

**Put the model id in an env var** (`OPENAI_MODEL`, default `gpt-6-luna`). Given OpenAI's pace (three
small-model generations in 14 months), the next swap should be a config change, not a code change.

> 🔁 Update `context/project-overview.md` (Tech Stack → AI, and §F) from `gpt-5-nano` to `gpt-6-luna` when
> this is approved.

### Per-feature settings

| Feature | Output | Reasoning effort | `max_output_tokens` | Input cap |
|---|---|---|---|---|
| Auto-tag | JSON `{ tags: string[] }` (≤ 5) | `none` | 200 | 8,000 chars |
| Summary | JSON `{ summary: string }` (≤ 1,000 chars, the `description` limit) | `none` | 400 | 12,000 chars |
| Explain code | Markdown, **streamed** | `low` | 2,000 | 40,000 chars |
| Prompt optimizer | JSON `{ prompt: string, changes: string[] }` | `low` | 3,000 | 20,000 chars |

`max_output_tokens` counts reasoning tokens as well as visible ones, so an effort level above `low`
makes truncation more likely. If a response comes back `status: "incomplete"` with
`incomplete_details.reason === "max_output_tokens"`, treat it as an error and don't show a partial result.

## 2. SDK setup

```bash
npm install openai   # v7.36.0 at time of writing; peer dep zod ^3.25 || ^4.0 — our zod ^4.4 is fine
```

`OPENAI_API_KEY` is already in `.env.example`. Add:

```bash
# Model for every AI feature. Swap here when OpenAI retires it — see docs/ai-integration-plan.md §1
OPENAI_MODEL=gpt-6-luna
```

### `src/lib/openai.ts`: a lazy client, the same pattern as `src/lib/email/resend.ts`

The `OpenAI` constructor throws when no key is set. If it ran at import time, every build and test
run without the key would fail.

```ts
import OpenAI from "openai";

let client: OpenAI | null = null;

export function getOpenAI(): OpenAI {
  if (!client) {
    const apiKey = process.env.OPENAI_API_KEY;
    if (!apiKey) throw new Error("OPENAI_API_KEY is not set");
    client = new OpenAI({
      apiKey,
      // The SDK default is 10 minutes. Nothing here should take more than a few seconds,
      // and a hung call holds a Vercel function open
      timeout: 30_000,
      // Default 2. One retry covers a transient 5xx/429 without doubling a slow failure
      maxRetries: 1,
    });
  }
  return client;
}

export function aiModel(): string {
  return process.env.OPENAI_MODEL || "gpt-6-luna";
}
```

Unit tests mock `@/lib/openai` the same way they mock `@/lib/r2`. Add it to the "mock everything
that leaves the process" list in `context/coding-standards.md` and `context/ai-interaction.md`.

### Structured call — `responses.parse` + Zod

```ts
import { zodTextFormat } from "openai/helpers/zod";
import { z } from "zod";

const TagSuggestions = z.object({ tags: z.array(z.string()).max(5) });

const response = await getOpenAI().responses.parse({
  model: aiModel(),
  instructions: TAG_INSTRUCTIONS,         // static: keep it first, it's the cacheable prefix
  input: buildTagInput(item),             // dynamic: the item's title/type/content
  reasoning: { effort: "none" },
  max_output_tokens: 200,
  text: { format: zodTextFormat(TagSuggestions, "tag_suggestions") },
  store: false,                           // §8
  safety_identifier: hashedUserId,        // §8
});
const parsed = response.output_parsed;    // typed, or null on refusal/incomplete
```

Structured outputs guarantee the JSON *shape*. They don't guarantee the content. The tags still go
through `normalizeTags` and the `TAG_MAX` / `TAGS_MAX` limits from `src/lib/validation/items.ts`, and
a summary is still clamped to `DESCRIPTION_MAX`.

## 3. Transport: Route Handlers, not Server Actions

The research prompt asks for "server action patterns". After checking the Next.js docs, I'm
recommending against Server Actions for these calls:

> "Next.js dispatches Server Actions one at a time per client. If a user triggers three actions in
> quick succession, the second waits for the first to finish… If you need parallel work… use a Route
> Handler for non-mutation requests." — Next.js docs, *Server Actions → Sequential dispatch on the client*

An AI suggestion takes 1–4 s, and an explanation can stream for 10 s or more. If those were Server
Actions, clicking **Save**, ⭐ or 📌 while "Suggest tags" was running would sit in the client queue
until the AI call finished. Server Actions also can't stream incrementally to the client: the reducer
does one fetch and waits for the whole Flight payload.

The calls also fit the coding standards' own rule for when to use a Route Handler: they are
**non-mutations** (§4), they need **specific status codes** (403 upgrade, 429 with `Retry-After`), and
explain is a **long-running/streamed** operation. `src/app/api/items/upload/route.ts` is the template:
it authenticates itself, uses `parseJsonBody`, runs the Pro gate before the rate limit, and returns
`{ success, data, error, upgrade }`.

```
src/app/api/ai/tags/route.ts        POST → { success, data: { tags } }
src/app/api/ai/summary/route.ts     POST → { success, data: { summary } }
src/app/api/ai/optimize/route.ts    POST → { success, data: { prompt, changes } }
src/app/api/ai/explain/route.ts     POST → text/plain stream (errors before the stream starts are JSON)
src/lib/ai/                         prompts, input builders, the shared guard, output post-processing
src/lib/validation/ai.ts            request schemas
```

The proxy matcher covers pages, not `/api/...`, so each route calls `auth()` itself, like
`/api/items/[id]` and `/api/items/upload` do.

### The shared guard, in this order

The order matches the upload route. Cheap rejections come first, so a malformed or Free request
doesn't spend rate-limit budget.

```ts
// src/lib/ai/guard.ts — sketch
export async function guardAiRequest(request: Request, schema): Promise<Guarded> {
  const userId = (await auth())?.user?.id;
  if (!userId) return { response: json(401, "Not signed in") };

  const parsed = await parseJsonBody(request, schema, { invalid: "Invalid request" });
  if (parsed.response) return { response: parsed.response };

  const plan = await getPlanUsage(userId);
  if (!plan || !checkProFeature(plan)) {
    return { response: json(403, DENIAL_MESSAGES.PRO_AI, { upgrade: true }) };
  }

  const limit = await checkRateLimit("ai", userId);
  if (!limit.success) return { response: tooManyRequests(limit) };

  return { userId, data: parsed.data };
}
```

### What the request carries

The request sends the **draft text from the form**, not an `itemId`. Suggestions are wanted while
creating an item, before any id exists, and while editing, when the saved row is stale. The draft
belongs to the caller and the response goes back only to them, so the server has no ownership to
check. The input only needs bounding (the caps in §1 sit far below `CONTENT_MAX`). That spares a DB
read, and the endpoint stays a pure function of its input, which makes it easy to test.

```ts
// src/lib/validation/ai.ts — sketch
export const tagRequestSchema = z.object({
  typeName: z.string().max(50),                 // "Snippet", "Prompt"… gives the model context
  title: z.string().trim().max(200),
  content: z.string().max(100_000),             // truncated to the feature cap server-side
  language: z.string().max(50).nullable(),
  existingTags: z.array(z.string().max(50)).max(20),   // so it suggests *new* ones
});
```

The server **truncates** to the cap rather than rejecting. A 60k-character snippet should still get
tags based on its first 8k characters. Tell the model when the input was truncated.

## 4. Streaming vs non-streaming

| Feature | Mode | Why |
|---|---|---|
| Tags | Non-streaming, structured | Tags appear as a set of chips; half a tag list is useless. They arrive in about 1 s |
| Summary | Non-streaming, structured | One sentence or a short paragraph, fast enough without streaming, and it's accept/reject as a whole |
| Optimize | Non-streaming, structured | The user needs the complete rewrite *and* the list of changes to judge it. A partial prompt can't be accepted |
| **Explain** | **Streamed** | Long-form markdown that's read top to bottom. Seeing words in about 300 ms instead of waiting 10 s is the difference between the feature feeling fast and feeling broken |

### Explain: streaming sketch

```ts
// src/app/api/ai/explain/route.ts — sketch
export async function POST(request: Request) {
  const guarded = await guardAiRequest(request, explainRequestSchema);
  if (guarded.response) return guarded.response;          // JSON 400/401/403/429, before any stream

  const upstream = await getOpenAI().responses.create({
    model: aiModel(),
    instructions: EXPLAIN_INSTRUCTIONS,
    input: buildExplainInput(guarded.data),
    reasoning: { effort: "low" },
    max_output_tokens: 2_000,
    stream: true,
    store: false,
    safety_identifier: hashUserId(guarded.userId),
  }, { signal: request.signal });                          // client closes drawer → stop paying for tokens

  const encoder = new TextEncoder();
  const body = new ReadableStream({
    async start(controller) {
      try {
        for await (const event of upstream) {
          if (event.type === "response.output_text.delta") {
            controller.enqueue(encoder.encode(event.delta));
          } else if (event.type === "response.failed" || event.type === "error") {
            controller.error(new Error("explain failed"));
            return;
          }
        }
        controller.close();
      } catch (error) {
        console.error("explain stream failed", error);
        controller.error(error);
      }
    },
  });

  return new Response(body, {
    headers: { "Content-Type": "text/plain; charset=utf-8", "X-Content-Type-Options": "nosniff" },
  });
}
```

The client reads it with `fetch` + `response.body.getReader()` and appends each chunk to state that
`react-markdown` renders. There's no `EventSource`, because that is GET-only and can't send a body.
An error that happens mid-stream can't change the HTTP status any more. The client sees the reader
reject, keeps whatever already arrived, and shows an "Explanation interrupted — retry" line under it.

**The Vercel AI SDK (`ai`, `@ai-sdk/openai`) is the obvious alternative.** Its `streamText` +
`useCompletion` would replace the handler and the reader above. I'd leave it out: one streamed
feature doesn't justify a second abstraction layer over the SDK, and the plain version is about 30
lines that match the codebase's existing style. Reconsider if chat-style features get added.

## 5. Error handling and rate limiting

### OpenAI errors → user-facing responses

The SDK throws typed errors. Map them once, in `src/lib/ai/errors.ts`:

| SDK error | Meaning | Response to client | Log? |
|---|---|---|---|
| `OpenAI.RateLimitError` (429) — `insufficient_quota` | **Budget cap hit / billing** | 503 "AI features are temporarily unavailable." | `console.error`, the one to alert on |
| `OpenAI.RateLimitError` (429) — rate | Org RPM/TPM exceeded | 503 "AI is busy — try again in a moment." | warn |
| `OpenAI.APIConnectionTimeoutError` / `APIConnectionError` | Network or the 30 s timeout | 504 "AI took too long to respond." | warn |
| `OpenAI.BadRequestError` (400) | Our bug (schema, params) | 500 "Could not generate a suggestion." | error |
| `OpenAI.AuthenticationError` (401) | Key missing or revoked | 500, same generic message | error |
| `OpenAI.APIError` (≥500) | OpenAI outage (already retried once) | 503 | warn |
| `output_parsed === null` / `status: "incomplete"` / refusal | Model couldn't comply or ran out of tokens | 422 "Couldn't suggest anything for this item." | info |

Never pass OpenAI's error message through to the client. It can name the org, the model or quota
details. Every user-facing string is ours, in the `{ success, error }` shape that the existing
`toast.error(result.error ?? …)` call sites already read.

**OpenAI's 429 must not be passed on as our 429.** Our 429 means *you* hit *your* limit and carries a
`Retry-After` for that user. An upstream 429 is a server-side problem and returns 503.

### Our rate limit — the per-user budget

Add to `RATE_LIMITS` in `src/lib/rate-limit.ts`:

```ts
// Keyed by user id. Every call spends real money at OpenAI, so this is a
// cost ceiling more than an abuse guard — sized so a Pro user tagging a
// backlog never notices it, and a script hammering it costs cents, not rand.
ai: { limit: 30, window: "10 m" },
```

That is one shared bucket across the four features. Separate buckets would quadruple the worst case
without helping honest users. 30 per 10 minutes allows a burst of backlog tagging, and the worst case
is about 4,300 calls a day, roughly $8.60 if all of them were explanations. That figure is the reason
for the next point.

**AI should fail closed, unlike the auth limits.** `checkRateLimit` fails *open* on purpose: an
Upstash outage must not lock everyone out of sign-in. For AI the trade goes the other way, because a
missing `UPSTASH_REDIS_REST_URL` would silently remove the only per-user spend ceiling. Add an option:

```ts
checkRateLimit("ai", userId, { failClosed: true })
// no limiter / Upstash error → { success: false, retryAfterSeconds: 60 } and a console.error
```

Losing AI for the length of an Upstash outage is an acceptable failure. Unbounded OpenAI spend is
not. In local dev without Upstash this disables AI. Either set the Upstash vars locally (the free
tier is fine) or let `failClosed` relax when `NODE_ENV !== "production"`, and say which one in
`.env.example`.

Upstash's free tier allows 10k commands a day. Each `limit()` call is about 2 commands, so AI use
eats into the same budget as auth. That's fine at demo scale and worth knowing.

### Client-side

- Disable the trigger button while a request is in flight (one click = one call).
- Debounce nothing automatically. **No AI call runs without a click**: no auto-tag on every keystroke
  or on every save. The homepage line "Auto-tag suggestions on every save" (`AiSection.tsx`) should
  become "one click"; an automatic call on every save spends quota the user didn't choose to spend.
- Abort explain's `fetch` with an `AbortController` when the drawer closes. The route passes
  `request.signal` upstream, so OpenAI stops generating and stops billing.

## 6. Pro gating

Use the gate that's already there, unchanged:

```ts
// src/lib/entitlements.ts already says:
/** Pro-only features: uploads now; AI, export and custom types once they ship. */
export function checkProFeature(plan: ProAccessFields, now = new Date()): boolean
```

- Add `PRO_AI: "AI features are part of Pro."` to `Denial` / `DENIAL_MESSAGES` and return it with
  `upgrade: true` and status 403, as the upload route does with `PRO_TYPE`. The existing toast then
  offers the upgrade link.
- **Server-side is the only real gate.** The UI hides or locks the AI buttons for Free users (the
  shell already computes `checkProFeature(plan)` in `AppShell.tsx` to lock File/Image in the sidebar;
  thread that boolean down to `ItemDrawerProvider`), but a Free user calling `/api/ai/tags` with
  `curl` must still get 403. That case is the first test to write.
- When `BILLING_ENFORCED` is unset, `checkProFeature` returns true for everyone. **On the demo,
  every registered account gets AI**, so in that configuration the per-user rate limit and the OpenAI
  project budget (§7) are the only spend controls. That's acceptable, but the budget has to be set
  before the demo URL is shared.
- `hasProAccess` already handles the grace period, so a cancelled user keeps AI until
  `currentPeriodEnd` plus 24 h, the same as uploads.

### UI for Free users

Show the AI buttons with a small 🔒 Pro badge rather than hiding them, so Free users can see the
feature exists. Clicking opens the existing upgrade path instead of calling the API. Keep the
locked buttons out of the tab order.

## 7. Cost optimization

### Estimated cost per call (`gpt-6-luna`, Standard tier)

Assuming about 4 characters per token:

| Feature | Input tokens (typical / cap) | Output tokens | Cost per call (typical) | Worst case |
|---|---|---|---|---|
| Tags | ~600 / 2,300 | ~40 | **$0.00008** | $0.0003 |
| Summary | ~800 / 3,300 | ~80 | **$0.0001** | $0.0005 |
| Optimize | ~700 / 5,300 | ~600 (+ ~300 reasoning) | **$0.0005** | $0.002 |
| Explain | ~1,500 / 10,300 | ~800 (+ ~400 reasoning) | **$0.0008** | $0.002 |

A heavy Pro user making 50 calls a day costs about **$0.03 a day, roughly $1 a month**. Against R135
(about $7.40) of revenue that's fine, so cost isn't a reason to lower quality. The controls below
protect against the long tail and against abuse.

### The controls, by impact

1. **Hard monthly budget on the OpenAI project** (dashboard → project → Limits). This is the real
   backstop and the only one that still works if our code has a bug. Use a dedicated *DevStash*
   project with its own key, a budget around $5 for the demo, and an email alert at 50%.
2. **Input caps** (§1). A truncated 100k-char paste costs 10k tokens instead of 25k.
3. **`max_output_tokens`** on every call. Without it a looping generation runs on until the token
   limit, and you pay for every token.
4. **Reasoning effort `none`/`low`.** Reasoning tokens are billed as output at $0.50/M, and the
   default `medium` would multiply tag and summary costs several times over for no gain.
5. **No automatic calls** (§5).
6. **Abort on close** for explain (§5).
7. **Prompt caching: essentially automatic, and small here.** GPT-5.6+ models cache prefixes of at
   least **1,024 tokens**. Our instructions are about 200–400 tokens, so most calls fall below the
   minimum. Still, keep instructions static and first and put user content last, so the large
   explain/optimize inputs that do pass 1,024 tokens get the 90% cached-input discount when the same
   item is explained twice. `prompt_cache_key` isn't needed: routing is automatic on GPT-5.6+.
8. **Not worth it:** Batch/Flex (50% off, but async with minutes to hours of latency, which is wrong
   for click-and-wait UI), or caching AI results in Redis (the same input is rarely repeated, and
   the stored suggestion would go stale).

### Track usage

Log `response.usage` (`input_tokens`, `output_tokens`, `reasoning_tokens`, `cached_tokens`) with the
feature name and user id on every call, as a single `console.info` JSON line. Vercel logs make that
queryable enough for a demo. Use a DB table only if per-user quotas become a product feature.

## 8. Security

### API key

- `OPENAI_API_KEY` is server-only: no `NEXT_PUBLIC_` prefix, ever. Add `import "server-only"` at
  the top of `src/lib/openai.ts` so that a client component importing it fails the build instead of
  shipping the module. `server-only` isn't used in the repo yet, but Next.js supports it out of the
  box.
- Use a **project-scoped key** limited to the Responses endpoint and the one model if the dashboard
  allows it, so a leaked key can only be spent on this.
- Set it in Vercel as an encrypted env var for Production and Preview separately. Preview deploys get
  the same budget-capped project, or no key at all.

### Data handling

- **`store: false`** on every call. The Responses API defaults to `store: true`, which keeps the
  response on OpenAI's side for later retrieval. Nothing here is multi-turn, so storage buys nothing
  and leaves users' snippets on OpenAI's side.
- **`safety_identifier`**: a SHA-256 of the user id, truncated to 64 chars. OpenAI uses it to
  attribute abuse to one end user instead of flagging the whole org. Send the hash, never the email
  or the raw cuid.
- Users store secrets in snippets and commands (`.env` lines, tokens). The AI features send content
  to a third party, so say so once in the UI ("Sends this item's content to OpenAI") and in the
  privacy wording. §10 covers what a real product owes here.

### Input sanitization and prompt injection

- **Validate and bound every request** with Zod (§3). That also caps cost.
- **Delimit user content.** Put it in the `input` (never in `instructions`), wrapped in clearly
  marked tags (`<item_content>…</item_content>`), and tell the model the block is data to analyse,
  not instructions. This doesn't *prevent* injection. It reduces accidental instruction-following
  when a stored prompt says "ignore the above and…", which **is exactly what the Prompt type
  stores**. The optimizer especially has to treat its input as text to rewrite, not text to obey.
- **Real risk is low by design.** Content and output both belong to the same user, nothing is shared
  between users, the model has **no tools** (no function calling, web search or file access), and
  nothing is written without the user clicking Accept. The worst a malicious prompt can do is make
  the user's own suggestion bad. If sharing or public collections ever ship, revisit this, because
  then one user's content would reach another user's AI call.

### Output handling

- Structured output goes back through the same validators as user input: `normalizeTags` plus the
  tag limits, and the `DESCRIPTION_MAX` clamp. **The model is an untrusted client.**
- Explain output is markdown rendered with `react-markdown`. Keep it **without `rehype-raw`**, so any
  HTML the model emits is shown as text, never parsed. That's the existing default, so this is a
  "don't add" rule. Links in the output should get `rel="noopener noreferrer"` and
  `target="_blank"` through `react-markdown`'s `components` override.
- No model output is ever used as a URL, a file path, a DB query or code to execute.

## 9. UI patterns

Every AI feature follows the same loop: **trigger → loading → suggestion → accept / reject**.
Accepting writes into the **drawer's form state** (`ItemFormFields` is already controlled through
`values` + `onChange`) and never to the database. The user still clicks Save, which runs the existing
validated `updateItem` / `createItem`. That keeps one write path, and Cancel undoes an accepted
suggestion for free.

| Feature | Where | Trigger | Suggestion UI | Accept |
|---|---|---|---|---|
| **Tags** | Edit/create form, beside the Tags field | `✨ Suggest` (ghost button, `Sparkles` icon) | Dashed-outline chips under the field, one per tag. Tags the item already has are filtered out | Click a chip to add that one, or **Add all**. ✕ dismisses the row |
| **Summary** | Edit/create form, beside Description | `✨ Summarize` | Muted card under the field with the text, **Use** / **Discard** | Fills Description. If it already had text, **Use** replaces it, and an inline "Undo" link holds the old value until save |
| **Optimize** | Prompt items, content section | `✨ Optimize prompt` | A dialog or drawer pane: side-by-side or inline **diff** of old vs new, plus the `changes[]` bullet list ("Added an output format", "Removed ambiguity in step 2") | **Replace content** / **Copy** / **Discard** |
| **Explain** | Snippet & Command items, **view mode** | `✨ Explain` | Collapsible "Explanation" section below the code, streaming markdown, with a blinking cursor while it streams | Nothing to accept. It's read-only. **Copy** and **Regenerate**; it disappears when the drawer closes |

### States to design

- **Loading (non-streamed):** the button shows a spinner and "Suggesting…". The field placeholder
  shows a skeleton chip row or a skeleton text line, matching the existing skeleton style. Don't
  cover the form; the user can keep typing.
- **Streaming:** text appears as it arrives. A **Stop** button replaces Explain and aborts the fetch.
- **Empty result:** an inline muted line, "No new tags to suggest," not an error toast.
- **Error:** a toast with our message (§5). The button resets so the user can retry.
- **Rate-limited:** a toast with the humanised wait from `rateLimitMessage`.
- **Free user:** the 🔒 Pro badge leads to the upgrade path (§6).
- **Stale suggestion:** if the content changes after a suggestion arrives, keep the suggestion but
  label it "based on an earlier version". Don't silently discard it.

### Implementation notes

- One hook, `src/hooks/use-ai-suggestion.ts`, handles the non-streamed POST (in-flight state, abort,
  toasting errors, the `upgrade` flag), and `use-ai-stream.ts` handles explain. The four buttons stay
  thin.
- Use the `Sparkles` lucide icon for every AI affordance. It's already the Prompt type's icon and
  reads as "AI" across the industry.
- Mark streaming regions `aria-live="polite"` so screen readers announce the explanation without
  reading every single delta. Updating per paragraph is fine.

## 10. 🏭 Production reference (not planned for DevStash)

What a real product would need beyond the demo:

- **Data-processing disclosure and DPA.** User content goes to OpenAI (a US sub-processor). POPIA
  in South Africa (and GDPR for EU users) requires naming it in the privacy policy and covering the
  cross-border transfer. Consider an opt-in toggle per account, and a "never send this item"
  flag for snippets that hold secrets.
- **Secret scrubbing before send.** Run a regex pass for obvious credentials (AWS keys,
  `sk-…`, `ghp_…`, PEM blocks, `password=` lines) and redact them from the input, or warn and require
  confirmation. Users will paste `.env` files into a "Command" or "Note".
- **Zero Data Retention.** It's available on request for eligible orgs. With it, OpenAI keeps no
  abuse-monitoring logs of request content.
- **Persistent usage metering.** A `AiUsage` table (`userId`, `feature`, tokens, cost, `createdAt`)
  for per-user monthly quotas shown in Settings, abuse investigation, and reconciling against the
  OpenAI invoice. Rate limiting via Upstash doesn't keep history.
- **Quota as a product feature.** For example "Pro includes 1,000 AI actions/month", enforced from
  the usage table, with the Upstash limit staying as the burst guard.
- **Model-migration runbook.** OpenAI has retired a small model about every six months. Keep a small
  eval set (20 fixed items with expected-ish tags and summaries) and run it against a new model
  before changing `OPENAI_MODEL`. Watch `GET /v1/models/{id}` `shutdown_date` in a scheduled check.
- **Moderation.** It isn't needed while all content stays with one user. Once anything is shared, run
  the free moderation endpoint on content and outputs before showing them to someone else.
- **Monitoring.** Alert on `insufficient_quota` (budget hit), on an AI error rate above about 5%,
  and on p95 latency. Track daily spend against the budget.
- **Fallback provider.** Optional. For an outage, route to a second model or provider behind the same
  `src/lib/ai/` interface. That's not worth it until AI is core to retention.

### Unit tests (route handlers + `src/lib/ai/`; mock `@/auth`, `@/lib/db/entitlements`, `@/lib/rate-limit`, `@/lib/openai`)

Security guards come first, per `context/ai-interaction.md`:

- 401 without a session. **403 + `upgrade: true` for a Free user with `BILLING_ENFORCED=true`**, and the
  OpenAI mock is **not called**. 200 for the same user when enforcement is off.
- 429 + `Retry-After` from our limiter, and the OpenAI mock is not called. The limiter **fails
  closed** when it's unavailable.
- 400 for over-length or malformed bodies. Over-cap content is **truncated**, not rejected (assert on
  what reached the mock).
- The OpenAI error mapping: `insufficient_quota` → 503, timeout → 504, refusal or `incomplete` → 422,
  and no upstream message ever leaks into `error`.
- Output post-processing: tags normalized, de-duplicated against `existingTags` and capped at 5, and
  the summary clamped to 1,000 chars.
- Every call sends `store: false`, `max_output_tokens` and a hashed `safety_identifier`, never the raw id.
- Explain: guard failures come back as JSON before any stream opens. A stream that hits
  `response.failed` errors the `ReadableStream`.
