- 2026-08-19: **Fix — OAuth Account Linking (GitHub ↔ Credentials)** - per context/features/fix-oauth-account-linking.md: registering with email/password then signing in with GitHub on the same address failed with NextAuth's `OAuthAccountNotLinked` (surfaced as "That email is already registered with a different sign-in method"), because `handleLoginOrRegister` finds a `User` row with a matching email but no `github` Account row and refuses to merge them. Fix is two parts: `GitHub({ allowDangerousEmailAccountLinking: true })` in src/auth.config.ts *permits* linking, and a new `signIn` callback in src/auth.ts *gates* it — verified against the Auth.js source that `handleAuthorized` (which invokes `signIn`) runs before `handleLoginOrRegister` (which links or throws), and that returning a string from `signIn` redirects. Decision table for a GitHub sign-in: no local user → allow (adapter creates); `github` Account already present → allow (ordinary sign-in); password account with `emailVerified` set → allow (adapter links); password account with `emailVerified` null → redirect to `/sign-in?error=AccountLinkBlocked`. The callback is merged as `callbacks: { ...authConfig.callbacks, signIn }` — **spreading first is load-bearing**, otherwise it clobbers the shared `session` callback that puts `user.id` on the session. It lives in auth.ts, not the edge config, because it needs Prisma; the proxy builds its own instance from auth.config *without* the gate, but its matcher is /dashboard/:path* so it never handles a sign-in. Fails closed — Auth.js wraps a throw inside `signIn` as `AccessDenied`, so a DB blip denies rather than allows. New `AccountLinkBlocked` code mapped in src/app/(auth)/sign-in/page.tsx to "That email already has a password account. Sign in with your password instead."
