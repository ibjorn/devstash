# Current Feature: Delete Item

## Status

In Progress

## Goals

- The Delete (trash) button in the item drawer's action bar — currently a "Deleting items is coming soon" toast in `src/components/items/ItemDrawerActions.tsx` — opens a shadcn **AlertDialog** confirmation naming the item
- Confirming deletes the item via a new `deleteItem` server action in `src/actions/items.ts`, returning the standard `{ success, error }` shape
- Ownership enforced **inside the delete's own where clause** (`where: { id, userId }`), so another user's item and a nonexistent id are the same "not found" result — no fetch-then-check window, matching `updateItem`
- On success: success toast, drawer closes, and the listing/dashboard refreshes (`router.refresh()`) so the card, counts, sidebar badges and stats drop the item
- On failure: error toast, dialog stays usable; confirm button shows a pending spinner and is disabled while in flight (same `Loader2 … animate-spin` treatment as the other submit buttons)
- Unit tests for the new query and action: auth guard never reaching the DB, runs as the session user, ownership in the where clause, not-found (P2025) mapped to a friendly error

- 2026-08-19: **Fix — OAuth Account Linking (GitHub ↔ Credentials)** - per context/features/fix-oauth-account-linking.md: registering with email/password then signing in with GitHub on the same address failed with NextAuth's `OAuthAccountNotLinked` (surfaced as "That email is already registered with a different sign-in method"), because `handleLoginOrRegister` finds a `User` row with a matching email but no `github` Account row and refuses to merge them. Decision table for a GitHub sign-in: no local user → allow (adapter creates); `github` Account already present → allow (ordinary sign-in); password account with `emailVerified` set → allow (adapter links); password account with `emailVerified` null → redirect to `/sign-in?error=AccountLinkBlocked`. Same class as the 2025 Strapi advisory (GHSA-2cjv-6wg9-f4f3 / CVE-2025-25298). **`.max(72)` alone does not fix it** — Zod counts UTF-16 code units, not bytes, so 30 emoji is length 60 but 120 bytes and sails through a character cap straight into the truncation; the guard that actually holds is a `TextEncoder().encode(v).length <= 72` refine, with `.max()` kept only for the friendlier message in the common ASCII case. **The audit's own File and Fix lines were wrong and were corrected in the report**: it claimed the shared `password` schema is used by `signInSchema`, but sign-in has its own `z.string().min(1)`, as does `changePasswordSchema.currentPassword` — and those two are precisely the fields that reach `bcrypt.compare`, so fixing only the shared schema would have left the unbounded-body half of the finding open on the sign-in path. Its suggested "friendlier UX cap like 100" was worse than doing nothing, since a 100-character cap *guarantees* the truncation it was meant to prevent. **The two comparison fields are deliberately capped loosely (1KB) rather than at 72**: bcrypt truncates a longer input to the same 72 bytes it hashed, so anyone whose password was set before this cap still signs in — rejecting at 72 would lock them out for no security gain, as the collision is already baked into their stored hash. No schema change, no migration, no new dependency. Verified by running the real schemas at every boundary: 72 ASCII accepted / 73 rejected, 18 emoji (=72 bytes) accepted / 24 emoji (=96 bytes) rejected where `.max()` alone would have passed it, a legacy 100-char sign-in password still accepted, 1025 rejected, and the existing mismatch/min-length refines still firing. Also checked rather than assumed: an over-72 ASCII password emits *two* issues on the same field, but all four consumers (RegisterForm, ResetPasswordForm, ChangePasswordDialog via `!(field in errors)` / `??=`, and the register route via `issues[0]`) are first-wins, so only "Password must be at most 72 characters" ever renders. lint + build pass. **Not verified in a browser** — no headless browser in WSL, and the change is validation-layer only, but the new copy has not been seen rendered. **Shipped alongside:** `.claude/agents/auth-auditor.md`, a read-only auditor subagent scoped to what NextAuth does *not* handle (hashing, rate limiting, token generation/expiry/single-use, enumeration oracles, session lifecycle) with an explicit do-not-flag list for what it does (CSRF, cookie flags, OAuth state, JWE signing), plus a verification gate requiring a written exploit sentence per finding.
